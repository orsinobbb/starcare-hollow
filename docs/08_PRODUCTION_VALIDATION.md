# 製作、技術與驗證計畫

> 版本：v0.6。已驗證「可愛配對＋玩家主動技能＋小鎮累積」，並先以一張原創 Canvas 地圖驗證逐格挖寶；分岔故事、換裝與大量美術維持後續擴充。

## 1. v0.6 已完成範圍

- 可直接由 GitHub Pages 遊玩的靜態網站。
- 小鎮首頁、四種共用資源、三座建築、升級、每日星願、修復階段與八件永久手札收藏。
- 翻牌記憶、雙雙消除、三件收納三種短關卡，以及驚喜輪替／單一模式選擇。
- 舒適、標準、專注三階難度；120 秒與三關的正式預設。
- 三種可主動施放的搭檔技能、連續數、分數、星級、重試與換盤。
- 星脈遠征 8×8 地圖：固定 seed、相鄰挖掘、三種地形成本、專注力、羅盤距離提示、遺物與小鎮獎勵。
- Canvas 地圖依 DPR 重繪、固定步長鏡頭慣性與粒子；拖曳手勢嚴格限制於地圖，頁面捲動與縮放不影響規則或存檔。
- schema v5 本機存檔、上一版備份、v1～v4 正規化、場次獎勵去重與遠征進度保留。
- 桌面、觸控、鍵盤、降低動態與自然頁面捲動。

## 2. 當前驗證問題

1. 三種玩法中，哪一種最想立刻再玩？
2. 驚喜輪替比鎖定單一玩法更有吸引力嗎？
3. 四組充能一次是否剛好，三招是否都有明確時機？
4. 120 秒三關是完整小段落，還是容易疲累／太快結束？
5. 玩家是否注意到結果真的回到小鎮、收藏與修復度？
6. 可愛圖案在手機小尺寸是否仍容易辨識且不傷眼？

## 3. 階段與出口條件

### A. v0.5 核心互動鎖定

- 5 位目標玩家各完成至少三場，其中一場選驚喜輪替。
- 90% 初玩者 60 秒內完成第一組。
- 所有人都能在不提示操作方式下返回小鎮並指出獎勵變化。
- 不出現「已消除但畫面仍在」、「點擊漏失」或滑頁被鎖住。
- 三種技能均被自然選用；若一招低於 15%，先改功能或呈現。

### B. 小鎮閉環

- 30 分鐘內至少完成一次採收、委託、小遊戲、領星願、升級或修復。
- 玩家能區分資源與永久收藏，並知道下一個短／中／長期目標。
- 連玩三日不被重複動作或等待時間卡住。

### C. v0.6 遠征切片

- 玩家在第一次 60 秒內能理解「只能挖相鄰格、地形會花專注力、羅盤指向尚未發現的遺物」。
- 每次合法挖掘先看見翻出的地形、羅盤文字與粒子；發現遺物時有清楚的獲得文字與圖示，不能只讓數字變動。
- 地圖拖曳只移動鏡頭；瀏覽器縮放、重新排版與頁面捲動不改變格子、seed、資源或存檔。
- 遠征必須在 10～15 分鐘內回饋至少一件永久收藏或可見的小鎮進度。

## 4. 技術架構

```text
prototype/index.html
  ├─ src/app.js       畫面流程、三模式狀態機、輸入與技能
  ├─ src/engine.js    純規則：洗牌、牌組、托盤、計分、充能
  ├─ src/expedition-engine.js  純規則：seed 地圖、挖掘、羅盤與獎勵事件
  ├─ src/expedition-renderer.js  Canvas：DPR、鏡頭、命中與粒子
  ├─ src/expedition.js  遠征 UI 與小鎮橋接
  ├─ src/town.js      小鎮狀態、經濟、收藏、存檔與遷移
  ├─ src/version.js   app／schema 版本
  └─ styles.css       響應式畫面、牌面、動畫與降低動態
```

原則：

- 規則函式不依賴 DOM，能以 Node 單元測試。
- 畫面只透過事件呼叫規則，重繪後 DOM 必須反映單一真實狀態。
- 新模式以獨立 `mode id`、牌組建立器、互動處理器與完成條件接入。
- 所有站內路徑使用相對 URL，保持 GitHub Pages 子路徑可部署。
- 不引入不必要框架；當內容量需要組件化或正式資產管線時再評估 Vite／遊戲引擎。

## 5. 狀態機

```text
briefing → running ↔ paused
              ↕ help
              ↓
       round transition → next round
              ↓
            result → retry／new board／town
```

`previewRemaining`、`compareRemaining`、`hintRemaining` 與 `transitionRemaining` 是彼此可測的短暫狀態。處於預覽、判定或轉場時，盤面按鈕暫停接受輸入，避免重複點擊造成資料與動畫錯位。

## 6. 存檔與遷移

- 正式 key：`starcare-hollow:town:v1`；保留穩定 key，版本放在內容內。
- 備份 key：`starcare-hollow:town:backup`。
- v0.6 使用 schema v5；新增 `expedition` 地圖快照、`expeditionDigs`、`relicsFound` 與完成次數；v1～v4 會補上新地圖而不覆寫既有資源、建築與收藏。
- 未知高版本、非物件或壞掉 JSON 不直接覆寫；以安全新狀態啟動並保留原始備份。
- 結算 id 去重，避免返回、刷新或重複事件發獎。
- 每次 schema 變更都要加入舊資料 fixture 與遷移測試。

## 7. 自動化測試

`cd prototype && npm run check` 必須涵蓋：

- JavaScript 語法檢查。
- 固定 seed 洗牌與牌組數量。
- 二張／三張配對判定、托盤插入與三件消除。
- 輪替路線、技能充能、連續、計分與時間格式。
- 小鎮獎勵、收藏解鎖、每日循環、建築升級、存檔備份與 v1～v4 遷移。
- 固定 seed 地圖、相鄰挖掘、地形成本、羅盤提示、遺物事件與遠征獎勵。
- HTML 所需元素、相對資產路徑、版本一致與已移除舊介面。

測試通過只是最低門檻；每次玩家可見修改仍需瀏覽器實機走查。

## 8. 瀏覽器測試矩陣

| 情境 | 必測內容 |
|---|---|
| 桌面 1440×900 | 三欄資訊層級、三模式完成、三技能、遠征拖曳／點格、暫停、說明、結算 |
| 手機 390×844 | 垂直滑頁、牌面與地圖命中區、無水平溢位、固定導覽不遮擋；地圖外可捲動、地圖內可拖曳 |
| 鍵盤 | Tab 順序、Enter／Space 選卡、Escape 暫停與關閉說明 |
| 降低動態 | 無必要翻轉／粒子，狀態仍可辨 |
| 舊存檔 | v1、v2、v3 資源與收藏保留，新欄位補齊 |
| GitHub Pages | 子路徑資產 200、主控台無 error、重新整理仍可啟動 |

每個模式至少測一次成功與一次錯誤；三件收納另測托盤滿，翻牌另測預覽結束，技能另測能量不足與能量已滿。

## 9. 效能預算

- 首屏壓縮資源目標小於 3 MB；目前程式與 CSS 應遠低於此值。
- 盤面更新維持流暢，避免每動畫幀重建所有卡片；HUD 可節流至約 120 ms 更新。
- 正式角色圖使用 WebP／AVIF、尺寸分級與延遲載入。
- 同畫面高成本粒子上限 40；降低動態時降為 0～8。
- 中階手機連續三場不得明顯過熱或出現輸入延遲。

## 10. 美術交付順序

1. 八個卡片家族的正面圖、背面與消除狀態。
2. 三位搭檔頭像、待機、技能準備與施放演出。
3. 小遊戲屋桌面、收納托盤與三種模式標記。
4. 小鎮三座建築的 Lv.1～Lv.3 狀態。
5. 收藏卡與新物件獲得演出。

先用一個家族完成切圖、尺寸、透明邊、壓縮與載入測試，再批量生成。AI 圖不可直接承擔 UI 文字，正式文字由 HTML／CSS 呈現。

## 11. 發布流程

1. 更新程式、測試、版本號與更新紀錄。
2. 執行 `npm run check`。
3. 本機實測桌面與 390×844 手機。
4. 提交並推送 `main`，建立對應版本 tag。
5. 等待 GitHub Actions 的驗證與 Pages 部署成功。
6. 以公開網址重新測試入口、三模式、存檔與資產載入。

完整版本與回復規則見 [GitHub 發布與長期升級規格](09_GITHUB_RELEASE_UPGRADE.md)。

## 12. 完成定義

- 功能：三模式、三技能、星脈遠征、小鎮結算、收藏與升級形成閉環。
- 正確：自動測試全通過，畫面與狀態同步，獎勵不重複。
- 可用：桌面、手機、鍵盤、低動態與關閉聲音皆能遊玩。
- 可升級：模式規則與小鎮資料分離，schema 有遷移路徑。
- 可發布：GitHub Actions 成功，公開網址實機驗證且主控台無錯誤。
