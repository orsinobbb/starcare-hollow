# 製作、技術與驗證計畫

## 1. 製作原則

先證明核心因果「現場產生任務、盤面解決任務」好玩且清楚，再投入角色、故事和大量家具。每個階段都有停止或重設條件，不能用增加內容掩蓋核心問題。

## 2. 四個產品範圍

### 2.1 紙上／互動灰盒

**目的**：證明核心操作。  
**內容**：

- 7×6 任務盤。
- 四類任務珠。
- 一個簡化診所現場。
- 三種設備、三種病患。
- 三連、五連、七連與紊亂珠。
- 一個 180 秒班次。

**不做**：劇情、建造、美術、經濟、存檔。

### 2.2 垂直切片

**目的**：證明玩法、視覺、聲音和長期回饋能形成完整體驗。  
**內容**：

| 類別 | 範圍 |
|---|---|
| 地區 | 暖燈街一小區 |
| 班次 | 6 個，含一個迷你首領 |
| 任務珠 | 觀察、調製、療護、安撫 |
| 員工 | 莉歐娜、奧連、柯姆 |
| 主要居民 | 米菈、托比 |
| 一般病患 | 6 種基型 |
| 奇症 | 噴嚏雲、迴音語、星屑打嗝 |
| 設備 | 問診桌、診療床、藥劑台、茶席 |
| 建造 | 8×6 可改配置區域、12 件家具 |
| 生產 | 4 藥材、4 配方 |
| 故事 | 約 20 分鐘 |
| 音訊 | 一組動態音樂與完整核心音效 |
| 時長 | 初玩 45～75 分鐘 |

### 2.3 可公開試玩版

**目的**：驗證留存、理解、效能與市場定位。  
**內容**：

- 完整暖燈街 12 個主線班次。
- 3 個居民支線與 2 個自由門診模板。
- 4 名員工。
- 12 種病患、5 種奇症。
- 6 種設備、24 件家具。
- 8 種藥材、10 個配方。
- 第一個完整地標修復。
- 2～3 小時內容，存檔可承接正式版。

### 2.4 正式版願景

依總覽規模：六區、72 主線班次、12 名員工、30 種奇症與 180 件以上家具。只有試玩版數據達標後才鎖定完整量產。

## 3. 階段與出口條件

### 階段 A：概念鎖定

交付：

- 核心設計文件。
- A01～A08 概念圖。
- 任務珠可讀性測試。
- 兩個介面線框版本。

出口：

- 目標玩家能用自己的話描述遊戲核心。
- A02 畫面在 5 秒觀看後能指出診所與盤面的關係。
- 鎖定鏡頭、角色比例、核心色盤。

### 階段 B：核心灰盒

交付：

- 可用滑鼠與觸控操作的一局。
- 可視化需求生成、逾時與安定度。
- 固定種子重播和基本除錯面板。

出口：

- 10 分鐘內 80％玩家理解因果。
- 熟練三局後表現平均提高至少 20％。
- 至少 70％失敗者能指出可改策略。
- 沒有嚴重輸入延遲、無解盤面或狀態錯配。

重設條件：

- 玩家只盯盤面，完全不看診所。
- 玩家覺得任務珠和病患沒有關係。
- 成功主要取決於掉珠運氣。

### 階段 C：垂直切片

交付：

- 完整 45～75 分鐘流程。
- 一輪建造、生產、員工成長、居民故事和地標變化。
- 接近正式品質的一間診所與核心聲音。

出口：

- 70％目標玩家在結束時願意立即再玩一班。
- 80％能說出下一個短期與中期目標。
- 至少半數玩家主動調整過一次房間或隊伍。
- 核心畫面在目標最低硬體穩定 60 FPS。
- 無障礙關鍵流程全部可完成。

### 階段 D：公開試玩

交付：

- 第一章完整內容。
- 崩潰回報、匿名遙測同意流程、存檔遷移。
- 平衡與效能設定。

出口：

- 第一關完成率大於 90％。
- 第一章完成率大於 45％。
- 第一次遊玩中位數大於 35 分鐘。
- 因不理解而退出的比例低於 10％。
- 重複遊玩者中至少 35％嘗試三星或佈置。

## 4. 建議技術架構

引擎需經兩天核心輸入原型再選定。若團隊沒有既有技術包袱，建議優先比較 Godot 4 與 Unity LTS：

- Godot：單機 2D、開源、建置輕；需先驗證大量 UI 與目標平台工具鏈。
- Unity：2D 工具與人才較多；需評估授權、版本與套件依賴。

不因美術概念圖看似 3D 就直接決定使用 3D。正式方案要依角色動畫成本、建造遮擋和效能測試決定。

### 4.1 模組

    GameState
      ├─ ShiftSimulation
      │   ├─ PatientFlow
      │   ├─ StaffAI
      │   ├─ EquipmentQueue
      │   ├─ TaskBoard
      │   └─ ScoreResolver
      ├─ ClinicBuilder
      │   ├─ Grid
      │   ├─ Pathfinding
      │   └─ RoomTags
      ├─ MetaProgression
      │   ├─ Inventory
      │   ├─ Crafting
      │   ├─ StaffProgress
      │   └─ Collections
      ├─ Narrative
      ├─ SaveSystem
      └─ Presentation

模擬層不得直接依賴畫面動畫。如此才能做快速批次模擬、固定種子測試和低特效模式。

### 4.2 資料驅動

以下全部使用可驗證的資料表或資源檔，不硬寫在程式：

- TaskType
- PatientArchetype
- Ailment
- TreatmentRoute
- Equipment
- Staff
- Skill
- LevelDefinition
- RewardTable
- Recipe
- Furniture
- DialogueEvent
- DistrictState

每筆資料有穩定 ID，顯示文字使用獨立 localization key。

### 4.3 班次狀態機

    Loadout
      → Intro
      → WaveActive
      → Intermission
      → WaveActive
      → Result
      → RewardCommit

- RewardCommit 只執行一次並具交易性。
- 波次開始時保存可恢復快照。
- 暫停凍結模擬時間，不凍結純 UI 動畫時間。
- 固定模擬 tick，不以畫面幀率計算耐心。

### 4.4 存檔

- JSON 或二進位皆可，但要有 schemaVersion。
- 每次遷移保持原檔備份。
- 資源獎勵採事件 ID 去重，避免當機重複領取。
- 本機三槽、每槽十個輪替自動存檔。
- 存檔不包含可由資料庫重建的大型靜態內容。

## 5. 開發工具

垂直切片前必須有：

- 關卡編輯器：波次、病患、目標、修正器、獎勵。
- 診所格線檢查：入口到設備與出口的可達性。
- 任務盤種子檢視：逐步重播生成與輸入。
- 經濟模擬器：輸入玩家行為模型，輸出章節資源。
- 病患路徑熱圖。
- 字串缺漏與 UI 溢位掃描。
- 所有圖示灰階和三種色覺模擬預覽。
- 存檔升版測試器。

沒有這些工具時，72 個關卡和 180 件家具的品質無法穩定維護。

## 6. 自動化測試

### 6.1 任務盤

- 任意合法盤面至少有一個三連，否則自動重排。
- 危急保證在指定五顆內出現足夠類型。
- 特殊珠連鎖不重複結算。
- 重排不改變等待計時。
- 固定種子和同一輸入得到同一結果。

### 6.2 診所

- 所有病患可從入口到必要設備再到出口。
- 設備拆除時安全處理佇列。
- 員工重新指派不產生兩個實體或卡死。
- 暫停與切換速度不改變總模擬結果。
- 牆體調整後路徑快取正確失效。

### 6.3 經濟

- 獎勵事件不可重複領取。
- 只推主線模型無需刷關即可買必要設備。
- 暫存箱不會吞掉超額材料。
- 製作完成跨越離線與夏令時間仍正確。
- 重複收藏轉換與保底計數正確。

## 7. 測試矩陣

| 面向 | 最低測試 |
|---|---|
| 解析度 | 1280×720、1920×1080、2560×1600、超寬安全區 |
| 輸入 | 滑鼠、觸控板、觸控螢幕、鍵盤替代操作 |
| 效能 | 低階整合顯示、主流筆電、平板候選機 |
| 人數壓力 | 1、6、10、15 名現場角色 |
| 盤面 | 正常、高連鎖、全急迫、多特殊珠 |
| 字串 | 繁中、英文、1.4 倍長度假語言 |
| 色覺 | 一般、紅綠、藍黃、全灰階 |
| 存檔 | 新檔、舊版升級、中斷寫入、空間不足 |
| 遊玩型 | 技巧、經營、收藏、只推故事、無障礙輔助 |

## 8. 效能預算

60 FPS 目標下每幀 16.67 ms：

- 模擬與路徑：最多 3 ms。
- 任務盤與輸入：最多 2 ms。
- UI：最多 3 ms。
- 動畫與渲染提交：最多 6 ms。
- 餘裕：至少 2.67 ms。

其他預算：

- 一般遊玩記憶體目標低於 2 GB。
- 切換班次載入低於 5 秒；重試低於 2 秒。
- 同畫面粒子上限依設備分級，低設定保留遊戲資訊。
- 存檔寫入不阻塞操作超過 50 ms。

## 9. 內容製作管線

每個新奇症依序完成：

1. 一句玩法意圖與情感隱喻。
2. 灰盒盤面機制。
3. 與現有設備、員工的組合矩陣。
4. 三個難度層的測試關。
5. 視覺與聲音概念。
6. 病患動畫與病例文字。
7. 無障礙替代提示。
8. 自動模擬與人工測試。

每個新關卡依序完成：

1. 一個主要教學或檢定意圖。
2. 病患波次與設備限制。
3. 無永久升級的基準通關測試。
4. 三星與星冠條件。
5. 故事包裝。
6. 獎勵和經濟檢查。
7. 三種難度及中斷恢復測試。

## 10. 團隊職能

最小垂直切片需要有人明確負責：

- 遊戲設計／製作：範圍、關卡、數值與測試。
- 程式：核心盤面、模擬、工具、存檔。
- 技術美術／美術：等角管線、角色、UI 與效能。
- 敘事／在地化編輯：角色語氣、病例、字串架構。
- 音訊：可在切片後段外包，但需早期定義音效事件。
- QA／玩家研究：可由團隊兼任，但測試記錄和決策需獨立於創作者直覺。

一人團隊可身兼多職，但仍需依此順序交付，避免同時展開全部內容。

## 11. 主要風險

| 風險 | 早期訊號 | 對策 |
|---|---|---|
| 上下畫面注意力分裂 | 玩家只盯盤或一直漏病患 | 需求光線、危機聚焦、降低現場手動頻率 |
| 核心隨機感太強 | 玩家把失敗歸因掉珠 | 壓力權重、保證機制、固定種子比較 |
| 經營對關卡不重要 | 玩家從不改配置 | 關卡路線條件、設備互斥分支、熱圖回饋 |
| 系統過多 | 前 30 分鐘大量選單未理解 | 分章解鎖、每次只教一動詞 |
| AI 美術不一致 | 同角色臉、比例、服裝變動 | 先鎖角色表、固定參考、正式資產人工描修 |
| 等角資產成本失控 | 每物件需多方向重畫 | 先測骨架／3D 混合，限制必要方向 |
| 生產等待變成阻礙 | 玩家缺道具不能玩主線 | 核心免費、製作只提供選擇與委託 |
| 內容量超出團隊 | 首章未完成便開始六區 | 嚴守灰盒、切片、試玩三道決策門 |

## 12. 垂直切片待辦順序

1. 用純色圓與方塊做 7×6 任務盤。
2. 建立病患步驟、設備佇列和任務珠生成。
3. 完成連線、特殊珠、急迫與紊亂。
4. 加入安定度、波次、評分與重試。
5. 完成固定種子、重播和除錯視圖。
6. 測試上下畫面注意力，必要時重設比例。
7. 加入一名員工與一個技能。
8. 加入最小建造與路徑檢查。
9. 接上班次結算、幣、單一設備升級。
10. 加入首批核准美術與音效。
11. 製作六關、兩名居民和地標修復。
12. 做 UX、無障礙、效能與外部測試。

任何時候若第 2～6 步未達核心出口條件，停止增加角色與家具。

## 13. 玩家測試訪談

不問「好不好玩」作為主要證據。每局後詢問：

1. 剛才最需要注意的是什麼？
2. 任務珠為什麼會出現？
3. 你在哪個瞬間覺得是自己的決定救回局面？
4. 如果再玩一次，你會改什麼？
5. 目前最想完成哪一件事？為什麼？
6. 有哪個資訊你知道很重要，但來不及看？
7. 哪個畫面或聲音最干擾？

觀察資料包括首次有效連線時間、現場注視比例、逾時類型、配置修改和離開點。

## 14. 完成定義

一項功能只有同時滿足以下條件才算完成：

- 設計規則和邊界條件已寫入資料／文件。
- 正常流程、失敗與中斷均可運作。
- 有必要的視覺、聲音與文字回饋。
- 滑鼠、觸控和替代操作可用。
- 通過對應自動測試與人工驗收。
- 有資料分析或除錯入口。
- 存檔相容與在地化字串已處理。

「畫面上看得到」不等於完成。

## 15. 最近的下一步

目前不應開始正式版內容量產。下一步依序是：

1. 產出並回傳 A01～A08 八張概念驗證圖。
2. 選定最接近目標的角色、場景、UI 和任務珠語言。
3. 做一個只有四類珠、三設備、三病患的灰盒班次。
4. 找 5～8 位符合目標輪廓的玩家進行三局測試。
5. 根據視線、理解和重試意願決定是否進入垂直切片。
