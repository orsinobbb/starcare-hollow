# 製作、技術與驗證計畫

版本：v0.4。先證明「看懂可愛居民的需求、正確派站、累積並選擇搭檔技能」好玩，再擴增故事、建造與大量收藏。串珠盤面已退出產品方向。

## 1. 現況與產品範圍

### v0.4 GitHub Pages 原型

已包含：

- 小鎮主畫面、三座可升級建築、每日星願、資源與八項收藏。
- 180 秒療癒所班次、八位居民、四座站點與三種難度。
- 三位可愛搭檔主動技能與共用充能。
- 流暢度、分數、星級、班次獎勵與回到小鎮的持久化。
- 本地存檔、備份、舊版遷移、重複班次獎勵防護。
- 響應式桌機／手機版與鍵盤基本可操作性。
- 純靜態部署，可直接由 GitHub Pages 提供。

### 垂直切片

下一個可對外測試的完整體驗：

- 暖燈街一區，90～120 分鐘內容。
- 12 個主線班次、6 個居民支線、1 個多階段星潮事件。
- 3 名正式員工、8 位居民、3 位搭檔、4 座站點。
- 療癒所房間佈置、藥園、工坊與 30～40 件家具。
- 24 件跨類型收藏與第一段分岔回溯。
- 正式插圖、角色動畫、音效、字幕與完整無障礙選項。

### 公開試玩版

- 兩個地區、約 4～6 小時內容。
- 6 名員工、18 位居民、6 位搭檔、8 座站點。
- 60～80 件家具、50 件以上收藏、至少 3 個真分岔節點。
- 匯出／匯入存檔、跨版本遷移、錯誤回報與隱私同意。

### 正式版願景

- 六區、72 個主線班次、36 位常駐居民、12 名員工。
- 建造、換裝、關係、探索、收藏、分岔與可重玩挑戰整合。
- 單機可完整遊玩；聯網功能只做可選分享、拜訪與共同目標。

## 2. 階段與出口條件

### A. 核心互動鎖定

工作：

- 四類需求／站點的圖形與文字語言。
- 居民選取、耐心、冷卻、流暢度與技能充能。
- 三個技能各自有明確最佳情境。
- 360 px 手機與桌機輸入驗證。

出口條件：

- 8/10 名首次玩家在 60 秒內完成第一位居民。
- 8/10 名玩家能說出 Tsum Tsum 的借鑑點是「角色可愛與主動技能」，不是消除玩法。
- 按鈕沒有漏點、重複結算、畫面延遲更新或滑動畫面誤觸。
- 標準模式首班完成率 75～90％。

停止或重設條件：

- 玩家只按發亮按鈕，不知道自己照顧哪位居民。
- 三個技能有一個在所有情況都更好。
- 壓力主要來自視力、命中精度或等待冷卻。

### B. 小鎮閉環

工作：班次獎勵、每日星願、建築升級、收藏解鎖與可見修復。

出口條件：

- 完成班次後 5 秒內能指出小鎮哪裡改變。
- 收藏至少涵蓋四種非資源類型。
- 2～3 次短班次能達成第一個有意義的升級。
- 重整、重玩、跨版本載入不重複發一次性獎勵。

### C. 垂直切片

工作：第一章內容、正式美術音訊、關係與分岔、佈置、探索支線。

出口條件：

- 60％測試者自願繼續玩超過 45 分鐘。
- 70％能說出至少兩位居民和一位搭檔的個性。
- 80％理解短、中、長期目標各一項。
- 沒有阻擋流程的存檔、效能或無障礙缺陷。

### D. 公開試玩

工作：第二區、內容工具、遙測、回報流程與持續部署。

出口條件：

- 主要瀏覽器完成率、錯誤率與載入時間達標。
- 版本遷移經三個歷史存檔樣本驗證。
- 所有新內容均由資料配置，不需改寫核心流程。

## 3. 技術架構

目前採靜態 Web 架構：

```text
prototype/
├─ index.html          畫面骨架與語意結構
├─ styles.css          響應式視覺與狀態
├─ src/
│  ├─ app.js           畫面控制、班次狀態與事件
│  ├─ engine.js        純函式規則、站點與技能常數
│  ├─ town.js          小鎮、收藏、資源與存檔
│  └─ version.js       應用與存檔版本
└─ tests/              Node 內建測試
```

原則：

- `engine.js` 不依賴 DOM，保持可單元測試。
- `town.js` 的公開操作接受狀態並回傳結果，不直接相信 UI 數值。
- `app.js` 只在玩家操作後立即完整刷新；時間更新採節流，避免按鈕在點擊途中被替換。
- 所有玩法參數最終移到資料檔；角色、班次、站點與技能使用穩定 ID。
- 路徑使用相對 URL，確保專案型 GitHub Pages 能正常載入。

### 未來模組邊界

| 模組 | 責任 | 不可直接依賴 |
|---|---|---|
| ShiftSimulation | 時間、居民、工作、冷卻、分數 | DOM、存檔 |
| CompanionSkills | 技能目標、效果、充能 | 畫面動畫 |
| TownDomain | 建築、日常、資源、收藏 | 班次 DOM |
| NarrativeGraph | 節點、條件、選擇、已讀狀態 | 畫面元件 |
| SaveRepository | 序列化、備份、遷移、驗證 | 遊戲平衡 |
| UIAdapter | 畫面、輸入、焦點、公告 | 直接修改永久資料 |

## 4. 班次狀態機

```text
briefing → running ↔ paused/help → result → town
```

`running` 內部事件：

```text
spawn resident
→ select resident
→ choose station
→ validate type/cooldown
→ resolve work
→ update flow/charge/score
→ complete step or resident
→ spawn next / tick patience
→ end by time or stability
```

每個事件先改資料，再渲染；一次事件只結算一次。技能使用也走單一原子事件，避免完成工作與居民離場重複計分。

## 5. 資料與存檔

每個存檔包含：

- `schemaVersion`、`gameVersion`、時間戳。
- 小鎮資源、修復度、建築等級。
- 每日星願與是否領獎。
- 累積班次、居民服務、技能使用、採收與委託。
- 收藏 ID 與已領班次 ID 的有限歷史。

升級流程：讀原始資料 → 驗證版本範圍 → 補新欄位 → 限制數值 → 重算收藏 → 寫新存檔 → 保留上一份備份。

規則：

- 舊版本缺少 `skillUses` 時補 0，不清空其他進度。
- 未知未來版本拒絕覆寫，提示玩家匯出備份。
- 一次性獎勵以事件或班次 ID 去重。
- 正式版提供 JSON 匯出／匯入與三個手動存檔槽。

## 6. 自動化測試

### 規則層

- 固定 seed 產生穩定居民順序。
- 玩家選中居民優先於自動急迫排序。
- 工作量不會扣成負數，冷卻不低於 0。
- 流暢度只在五秒窗內累加。
- 充能停在 100％，施放後正確歸零。
- 三技能的目標、恢復與凍結範圍正確。

### 小鎮與存檔

- 資源不足不可升級，成功後只扣一次。
- 每日行動與班次獎勵不可重複領。
- 技能使用一次即解鎖對應紀念收藏。
- v1、v2 存檔遷移到 v3 後資料不丟失。
- 壞資料回退安全預設並保留可用備份。

### 靜態與部署

- HTML 必要 ID、按鈕語意、版本 query 與 meta 存在。
- 不存在舊任務盤、拖曳連線或觸控攔截器。
- 相對資產路徑在 GitHub 專案子路徑下可載入。
- GitHub Pages workflow 成功，公開 URL 回傳 200。

## 7. 瀏覽器測試矩陣

| 面向 | 測試 |
|---|---|
| 桌機 | Chrome、Edge、Firefox、Safari 最新兩版 |
| 手機 | 360×800、390×844、430×932；Android Chrome、iOS Safari |
| 輸入 | 滑鼠、觸控、純鍵盤、螢幕閱讀器基本流程 |
| 縮放 | 100％、150％、200％ |
| 動態 | 正常、降低動態、背景分頁後恢復 |
| 存檔 | 無資料、舊版、損壞、容量不足、重新整理 |
| 網路 | 首次上線、快取後離線、更新部署後刷新 |

關鍵 E2E：

1. 首頁進療癒所，開始班次。
2. 選居民，連續完成四次正確站點服務。
3. 確認充能 100％，施放任一技能。
4. 等待結算，確認技能次數與獎勵。
5. 回小鎮，確認資源、日常與三心共鳴徽記。
6. 重新整理，確認上述進度保留。

## 8. 效能預算

| 項目 | 目標 |
|---|---:|
| 初始壓縮下載 | 2 MB 內（正式插圖延遲載入） |
| 首次可互動 | 中階手機 3 秒內 |
| 核心互動回應 | 100 ms 內有可見回饋 |
| 動畫 | 目標 60 fps，最低 30 fps |
| 長任務記憶體 | 150 MB 內 |
| HUD 全量重繪 | 最多每 500 ms；操作後立即 |

正式角色圖採 WebP／AVIF 加 PNG 備援；非當前地區延遲載入。降低動態時停用非必要粒子與背景視差。

## 9. 內容製作管線

1. 企劃用穩定 ID 建立居民、需求序列、對話與獎勵。
2. 驗證器檢查未知站點、負工作量、循環分岔、重複收藏 ID。
3. 固定種子模擬通關率、站點壅塞與技能使用價值。
4. 在灰盒跑完後才綁正式插圖、動畫與音效。
5. 每個內容包通過鍵盤、手機、存檔與結算回歸測試。

繪圖 AI 輸出只作概念與原始素材；正式 UI 文字、九宮格、狀態圖與透明切件仍需人工整理。第一批圖以 `06_ART_DIRECTION_AI_ASSET_BRIEFS.md` v0.4 提示為準。

## 10. 主要風險與護欄

| 風險 | 早期訊號 | 護欄 |
|---|---|---|
| 玩法又被誤解為消除 | 測試者尋找可連圖形 | 不放格子盤；教學直接用居民與站點動詞 |
| 可愛角色只是裝飾 | 玩家叫不出任何名字 | 肖像、需求、技能與獎勵都綁角色反應 |
| 技能沒有選擇 | 一招使用率過高 | 不同壓力情境、共享充能、追蹤使用率 |
| 冷卻造成等待 | 玩家盯著單一按鈕 | 多居民多站點交錯；冷卻短且獨立 |
| 小鎮只剩資源數字 | 玩家看不到累積 | 建築外觀、居民、收藏、故事同步變化 |
| 手機捲動誤觸 | 滑頁時觸發操作 | 班次只用單點；不攔截頁面觸控 |
| 更新破壞存檔 | 版本後進度歸零 | schema、遷移、備份、歷史樣本測試 |
| 文件再次漂移 | 新功能引用舊規則 | `01_CORE_GAMEPLAY.md` 為核心真源，PR 檢查禁用詞 |

## 11. 發布流程

1. 更新版本、變更紀錄、存檔 schema 與遷移測試。
2. 執行 `npm run check` 與 `git diff --check`。
3. 本機 HTTP 伺服器跑桌機、窄螢幕、完整班次與重整測試。
4. 提交並建立語意版本標籤。
5. 推送 `main` 與標籤，等待 GitHub Pages workflow 成功。
6. 公開 URL 做 HTTP 200、版本字串、核心互動與資產載入 smoke test。
7. 若失敗，依最後穩定標籤回復；不可在公開站直接試修。

詳細操作見 `09_GITHUB_RELEASE_UPGRADE.md`。

## 12. 完成定義

一個功能只有在以下條件全數成立才算完成：

- 規則、UI、文案、資料與文件一致。
- 正常、空狀態、錯誤、重複與中斷路徑都有處理。
- 自動測試通過，至少一條瀏覽器真實流程通過。
- 360 px、鍵盤、200％縮放與降低動態可用。
- 舊存檔能遷移，獎勵不能重複領。
- 公開 GitHub Pages 顯示正確版本且可從首頁完成核心流程。
